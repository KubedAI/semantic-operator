## Why agents get the number wrong

Ask an agent for sales per employee. It joins stores to sales and adds up the headcount.
That counts each store once for every sale it made, so the total is far too high.

Nothing fails. The query runs, the result is formatted neatly, and the number is off by
about ten thousand times. Unless you already knew the right answer, you would ship it.

We tested 30 business questions, each asked three different ways.

The fix is not a better prompt. It is deciding once, in one place, what a metric means, and
then never letting anything compute it another way.

## Three pieces, running on Kubernetes

<div class="so-cards-lg">
<CardGrid>
  <Card title="ossiectl writes the model" icon="laptop">
    Point it at your catalog and it generates the model. Tables, columns, and likely joins
    are filled in. Descriptions and PII tags can come from DataHub. You certify the metrics
    and the access rules.
  </Card>
  <Card title="The operator runs the lifecycle" icon="setting">
    Apply the model like any Kubernetes resource. It is validated, checked against the live
    database, compiled into a versioned artifact, and published. A drifted version is
    refused rather than served.
  </Card>
  <Card title="The server answers questions" icon="rocket">
    One request becomes exactly one SQL statement, with access rules already applied. MCP
    for agents, REST for applications, SQL views for BI. Stateless, so it scales sideways.
  </Card>
</CardGrid>
</div>

## Bring your own engine

The engine is two pluggable halves chosen by one setting. **StarRocks** and **Trino** ship
today, and the same model compiled for both returns identical numbers on a live cluster.
Glue, Polaris, Hive Metastore, and Unity all work through the engine's own catalog, and
your definitions stay portable because the model is plain
[Apache Ossie](https://ossie.apache.org/).
