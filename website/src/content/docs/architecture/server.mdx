The server is the query path. It holds no state of its own, writes nothing, and is the only
component that reads table data. Because all of its state lives in ConfigMaps and an
optional cache, replicas are interchangeable and it scales sideways.

## How a request becomes SQL

### Identity

The caller is resolved to a set of roles before anything else happens. Two modes exist and
the difference is a security boundary.

In `header` mode the roles are read from the `X-Semantic-Role` header, comma separated for
more than one. This is only safe behind a proxy that authenticates the caller and
overwrites that header, because otherwise any client that reaches the port can claim any
role. The chart refuses to install in this mode unless you also set
`server.auth.allowInsecureHeaderAuth`, and the server logs a warning at startup.

In `jwt` mode a bearer token is required and validated against the issuer's JWKS. Signature,
expiry, issuer, and audience are all checked, and only asymmetric algorithms are accepted
because the key set is public. Roles come from a role claim, a groups claim, or both, and
either may be nested. Any inbound `X-Semantic-Role` is ignored outright, so a caller cannot
assert its own identity.

An unverified caller gets 401. A verified caller that policy rejects gets 403. The
distinction matters when you are debugging.

### Discovery is governed too

Listing models, metrics, and dimensions goes through the same authentication as querying,
and through the same policy. A metric a caller could not query is left out of the listing
rather than shown and refused later, and so is a column their roles may not read. A listing
otherwise tells an unauthorised caller the shape of the warehouse.

Raw metric expressions are not returned unless you set `EXPOSE_METRIC_EXPRESSIONS`. The
expression is the definition itself, and an agent grounds perfectly well on the name, the
description, and the synonyms.

### Resolve and authorize

Metric and dimension names are looked up in the compiled model. Then governance runs,
**before any SQL exists**.

The check covers requested metrics against the role's allowlist, requested dimensions and
filters against denied fields, and every field inside every requested metric expression.
That last part is what stops a caller reading a forbidden column through an aggregate.

Roles do not pool their permissions. Some single role must permit the whole request on its
own, every metric and every field together. Combining them looks natural, because
Kubernetes RBAC is additive, but a policy carries restrictions as well as grants. Under
pooling, a role that grants nothing would cancel another role's denied fields and row
filters just by being present. A caller holding both would then see more than either role
allows.

### Plan

The planner picks the smallest join tree that connects the datasets the request needs. A
query touching only a dimension table does not detour through the fact table.

Ratio metrics get special care. If a ratio's denominator aggregates a dimension across a
join, summing it directly would multiply it by the number of fact rows. The planner splits
those into separate aggregations and deduplicates on the dimension's primary key. This is
the single most common way hand written and generated SQL produce a wrong number.

Ranking requests use `orderBy`. Each field must be a metric or dimension already requested,
and each direction must be `asc` or `desc`. The planner resolves fields to output columns.
It does not accept SQL expressions. When `orderBy` contains clauses, the planner emits
exactly those clauses and does not append hidden tie-breakers. An omitted or empty `orderBy`
retains the existing default ordering by requested dimensions. Ordering is applied before
the row limit.

```json
{
  "metrics": ["total_sales"],
  "dimensions": ["item.i_category"],
  "orderBy": [
    {"field": "total_sales", "direction": "desc"},
    {"field": "item.i_category", "direction": "asc"}
  ],
  "limit": 5
}
```

The dimension clause makes selection stable when categories have equal sales. Tie-breakers
are explicit. For a result grouped by several dimensions, include every dimension to
produce a complete and stable tie-breaker. A metric-only ordering remains valid, but tied
rows at the limit boundary may be returned in an engine-dependent order.

Row filters are conjoined within a role and disjoined across the roles that authorized the
request, so a caller sees the union of the rows those roles allow. A role that authorized
the request and carries no filters can see every row, which collapses the whole disjunction
rather than emitting SQL that looks restrictive and is not.

A predicate may interpolate a caller attribute, which is how "each user sees their own
region" is expressed.

```yaml
rowFilters:
  - dataset: store
    predicate: "region = {{claim.region}}"
```

The value is rendered through the dialect's literal function, so it is always an escaped
SQL literal. A caller whose token does not carry the claim is refused rather than served a
filter that silently matches the wrong rows.

Everything is rendered through the engine's dialect, so identifier quoting and literal
syntax match the target.

### Execute and report

One statement runs. The response carries the rows, the exact SQL, the model version, and a
request hash. Every statement begins with a comment holding those same three values, so a
query in the engine's log traces back to the request that caused it.

The same request, from the same identity, against the same model version, produces byte
identical SQL every time. Identity here means the roles and the claims together, because a
row filter can interpolate a claim. Two callers sharing a role but carrying different
tenants compile to different SQL, and never share a cached plan.

### What bounds a request

The server is a fixed size pod, so every part of a request is bounded. All of these are
Helm values under `server.query`, and the numbers below are the defaults.

| Bound | Default | What happens past it |
|---|---|---|
| Row limit | 1000, max 10000 | Refused, not truncated |
| Result size | 32 MiB | Abandoned while reading, before it is fully allocated |
| Request body | 1 MiB | Refused |
| Metrics, dimensions, filters | 25, 25, 50 | Refused |
| Values in one `IN` list | 1000 | Refused |
| Requests in flight | 4 | Queued briefly, then 503 with `Retry-After` |

A request over a bound is refused rather than trimmed. A silently truncated result cannot
be told apart from a complete one, which is the failure this whole system exists to
prevent, and there is no pagination yet to signal it.

The last two rows are one budget. Each in-flight request can hold a whole result until its
response has been written, so `maxConcurrent` multiplied by `maxResultBytes` has to stay
comfortably under the pod's memory limit. Raising either one means raising the memory limit
too.

## Three surfaces, one compiler

Agents connect over **MCP** and call `list_metrics`, `list_dimensions`, and `query_metric`.
The tool descriptions and the model's own synonyms let an agent ground a user's wording
onto a certified metric. The agent never writes SQL.

Applications use **REST**. `POST /v1/models/{model}/query` runs a request.
`POST /v1/models/{model}/sql` returns the plan without executing it, which is useful in
review and in tests.

BI tools read the **governed views** directly from the engine over its native protocol.

All three go through the same compiler, so they cannot disagree about what a metric means.

## Caching

An optional Valkey cache stores compiled plans and query results. Caching is an
optimisation and never a correctness dependency, so a cache miss or an unreachable cache
degrades to recompute and rerun.

The plan cache key includes the dialect, the model name, the model version, and a hash of
the request that already covers the effective role. Results are keyed on the emitted SQL,
which already contains any row filters. Both properties mean a cached entry cannot leak
across roles, versions, or engines.

## Access it needs

| Target | Access | Why |
|---|---|---|
| Engine model tables | SELECT | Executes the compiled statement |
| `configmaps` | get, list, watch | An informer keeps compiled models in memory |
| Valkey | Optional | Plan and result caches |
| JWKS endpoint | Read, in jwt mode | Validate bearer tokens |

It needs **no DDL of any kind**, no access to `SemanticModel` resources, and no catalog or
cloud credentials.

## Scaling and deployment

Stateless and horizontal. The default is two replicas and you scale on request rate.
Determinism makes the caches effective, so repeated questions can skip the engine entirely.

The Service is `ClusterIP` and the chart refuses any other type unless you explicitly
override it, because a load balancer in front of a header mode server is an unauthenticated
query endpoint. Reach it with `kubectl port-forward`, or put an authenticating ingress in
front and opt in deliberately.
